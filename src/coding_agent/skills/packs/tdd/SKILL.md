# Test-driven development

仿 Matt Pocock `tdd`（https://github.com/mattpocock/skills）的红绿循环，按本程序的 7 个工具落地。只注入本文件；没有 tests.md / mocking.md，也不调用其它 skill。

先 read_file / glob_search / grep 看仓库已有测试约定与公共入口。有 pytest 就跟 pytest，有其它跑法就跟现有走。用 bash 跑测试。能 edit_file 就不要整文件 write_file。

## 好测试测什么

测试验证公共接口上的行为，不绑实现细节。代码可以整段重写，测试不该跟着碎。一条好测试读起来像规格：「有效购物车可以结账」说的是能力，不关心内部结构。

期望值必须来自独立依据：字面量、算过的例子、规格。不要用和实现同一套算法当场算出「应该等于什么」。

## 缝：测哪里

**缝**是你观察行为的公共边界。测试只打在缝上，不打进私有方法或内部协作对象。

先写下本轮要测的缝，再写第一条测试。没确认的缝不写测试。不能什么都测，缝定在关键路径和复杂逻辑上。

问清楚：公共接口是什么，这一轮测哪几条缝。

## 不要这样做

- **绑死实现**：mock 内部对象、测私有方法、或绕开接口去查库。一重构就红、行为没变，就是这条。
- **同义反复**：断言只是把代码自己的算法再算一遍（`expect(add(a, b)).toBe(a + b)`、手推出来的快照、常量等于自己）。这种测试永远不会反对实现。
- **横切**：先写完全部测试再写实现。那是在测想象中的形状，不是用户能看见的行为。改成**纵切**：一条测试 → 刚好够过的实现 → 再下一条。

## 循环规则

- **先红后绿。** 先写会失败的测试，再用 bash 跑到失败；然后只写刚好让它通过的代码，再跑到通过。不要提前写后面几条，不要顺手加没人要的功能。
- **一次一切。** 每个循环：一条缝、一条测试、一份最小实现。
- **重构不在这个循环里。** 红绿只负责行为落地。整理结构放到测试绿了之后，另开一步，且仍用同一批测试守住行为。
